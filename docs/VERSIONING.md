# 版本与发布

网站「设置 → 版本与更新」和首页底部可查看版本、变化及历史记录。无需登录也可打开 `/updates`。

版本从 **0.1 → 0.11 → 0.12 → 0.13** 递增。版本是标识符，不是小数；0.19 的下一号为 0.20。工具内部使用三段格式，如 `0.11.0`，对外显示及启动器文件名仍为 `0.11`、`0.11.exe`。

## 一次更新怎样记录

1. 编辑 `cle/src/data/releases.json`。在现有待发布版本中记录变化；上一版发布后，在最前面新增下一版，并更新 `current`。历史条目保留。
2. 按「新增、修复、优化、使用与更新说明」填写中英文。至少有一项实际变化；手机号短信等未配置能力要注明条件。`draft` 的 `date` 可以为空。
3. 执行 `python scripts/versioning.py sync`，生成根目录 `VERSION`、`CHANGELOG.md`，同步前端 npm 锁文件和后端 Maven 版本。
4. 执行 `python scripts/versioning.py check`，再执行与改动相关的功能、权限、构建和安装测试。CI 会检查版本文件一致性。

状态含义：`draft` 为待发布开发版；`ready` 为已测试定版但尚未上传；`published` 表示 GitHub 安装文件已经实际发布并核验。本地源码版本可能领先于可下载版本，页面会明确区分。

## 打包与发布

1. 完成测试和版本说明，备份并验证升级所需的数据迁移；不要把 `.env`、用户数据或密钥加入 Git。
2. 将本次状态设为 `ready`，填写实际定版日期（`YYYY-MM-DD`），删除已经过时的“尚未准备”等说明，运行 `sync` 和 `check`，提交经过验证的源码。
3. 从该提交构建 Docker 应用镜像，然后运行 `python scripts/desktop/build-release.py --reuse-images`。脚本拒绝脏工作区或仍处于 draft 的版本，按 VERSION 自动生成 `output/release/0.11/0.11.exe`、对应运行包、镜像清单、版本说明和 SHA256SUMS。
4. MinIO 对应版本的源码归档仍是发布必需附件，须事先放入目标输出目录的 `minio-sources.tar.gz`。构建脚本不会把其他版本的源码归档自动冒充当前版本。
5. 在 GitHub 新建 **v0.11** 预发布（0.x 仍为测试版），使用生成的 `RELEASE-NOTES.md` 作为说明，上传清单列出的所有资产。不得覆盖历史 v0.1 的同名文件。
6. 核对下载地址、资产 SHA-256、启动器自检及保留数据的升级结果，再把版本状态改为 `published`、运行 `sync`，更新 README 的实际下载链接和安装说明。没有上传成功时继续保留待发布状态。

安装器显示版本、Windows 文件版本、运行包名称、镜像标签和 GitHub 下载路径均由同一版本生成。沿用 `%LOCALAPPDATA%\PKB-AI\0.1` 作为稳定安装目录，保留 `.env` 和原数据卷；目录名是历史兼容路径，不表示运行版本。不要同时启动旧、新启动器，也不要通过旧启动器降级带有数据库迁移的新版本。

旧 `revision` 仅用于验证历史 0.1 安装清单；新打包只生成修订 1，修复必须递增公开版本号。

本流程生成文件但不自动访问用户密钥、提交 Git、推送或上传 GitHub。发布时依然需要实际执行上述核验步骤。

仓库已有的镜像 CI 使用 `sha-<commit>` 作为不可变构建标识，标题、镜像元数据和说明会同时标注产品版本及变化。镜像构建与包含 Windows 启动器的 `v0.11` 发布分开，前者不代表后者已经提供下载。
